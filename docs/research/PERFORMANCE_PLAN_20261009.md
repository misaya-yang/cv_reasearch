# 端到端成本进入研究成功条件

用户最新明确要求：如果涨分依赖极端延迟，就不可用；在一小时内给出有依据的优化方案。由此更新此前“速度次要”的偏好：后续必须同时记录完整mIoU和真实端到端延迟，不能只报告缓存后几秒。

本轮已完成三项具体工作：

1. 定位M4 CPU CRF重复构图，单个真实九窗缓存案例占头部82.2%。区域分类通常不到1秒，参考原型不足1%，不把它们当主优化方向。
2. 已实现原数值的CRF几何复用并启用未来默认回放host。45个真实窗口与5个最终区域结果逐字节一致；ABBA完整缓存九窗头部38.867→14.023秒，2.772倍。DINO成本未包含，缓存有内存代价，不盲增并行/batch。
3. 同DeepGlobe100测试取消9个局部CRF、重新构建区域并融合：37.344028，对原版37.023712差+.320316，区间跨零；对同批FoRIS29.377542仍+7.966486。全图FoRIS引导的那次CRF仍保留。追加一次全图CRF只有32.987793，不采用；直接四角在LVIS200也损失4.034点，不扫组合。

数值不变优化可作为默认实现；快速算法仍是开发候选，需要已有LVIS/跨集缓存复核。之后测真实batch1冷/热参考及完整吞吐：9个局部编码仍存在，不能拿224秒的缓存100实验去对比原45.2分钟推导整轮倍率。

已补首例真实MPS FP32 batch1完整流水线：23.986秒，DINO11输入16.756秒、整图引导1.669秒、九窗无CRF头部4.978秒、区域.260秒；初始化另5.847秒。raw缓存读写0、query GT读取0，最终mask和封存快速版逐字节一致。单例不能代表100吞吐。最新人类提出查询只编码一次：后续优先研究整图特征共享后的局部提议与区域筛选，九次局部编码不能靠batch改名为一次编码；原生窗和全图裁取特征不同，既有未筛选窗口插值对照不能冒充当前区域版本的结果。

按用户追问补齐同进程、同首例、每臂真实重新编码的四臂完整成本：原FoRIS7.457秒、优化CRF的FoRIS4.435秒、老区域57.546秒、快区域22.605秒。老区域→快版2.546倍；以同样优化CRF的FoRIS为基线仍新增18.170秒，其中九窗编码12.576秒、九窗头部4.934秒、区域.261秒。因此当前只说“新增5秒”会漏掉主要增量；查询单次编码候选才可能去掉这部分。两个区域mask均与各自封存结果逐字节一致，原/优化FoRIS整图mask也一致。精确证据与限制：`cv_data/a/deepglobe_component100_20261009/performance/live_cost_compare/REPORT.md`及`result.json`。这是单例、不含模型初始化，不当作100例均值或INSID3时延。
