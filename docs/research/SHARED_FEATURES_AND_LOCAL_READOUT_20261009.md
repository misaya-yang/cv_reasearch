# 局部区域方法与卷积式共享计算

用户提出“像卷积”的观察成立于结构层面：各位置用相同读出规则、局部证据经重叠融合形成整图结果。对当前冻结DINO方法，最直接的效率启发是共享骨干与共同运算，而非继续把相同参考和整图任务重复处理。

## 与已有工作的位置关系

[FCN](https://arxiv.org/html/1411.4038v2)把卷积网络用于整图密集预测，减少逐块独立处理。[SPP-net](https://arxiv.org/html/1406.4729v4)明确将整图卷积特征计算一次，再在不同区域池化；[Fast R-CNN](https://arxiv.org/html/1504.08083v2)沿用共享整图特征图与RoI读出。我们的一次DINO+特征区域读取更接近后两者的计算结构。共享骨干/滑窗本身是成熟思想，不能单独作为新贡献。

[DINOv3原论文附录D.9](https://arxiv.org/html/2508.10104v1)的检测系统本身也组合全局视野与3×3局部视野，然后重组/融合特征。这支持区分全局上下文与局部尺度的设计意义，但不是我们具体3窗/9窗布局的最优性证明，也不是这100例分数的解释证据。我们没有引入其检测模型、训练、额外权重或多层特征。

## 当前方法为何不等于普通卷积

固定卷积在各位置用相同局部核；当前FoRIS局部读出还包含参考mask条件、去位置偏差开关、窗口内聚类与相对响应归一化。区域身份判断依赖全图FoRIS伪前景/背景和全图特征，最后又按连通区域接受或拒绝。因此它是任务条件下的局部提议与全局区域判别，不能直接宣称具有普通卷积的平移等变性或相同计算重用规律。

尤其一般有 `DINO(crop-and-resize(I)) != sample(DINO(I))`。本机原图1024、patch16，整图O24是64×64；512图像窗口放大1024再编码后仍是64×64，相当于原图8像素间距。整图特征裁取对应区域只含约32×32原始采样位置，插值64×64不产生新的输入细节；ViT的图像上下文与位置关系也改变。这是从实际预处理/表示构造可推出的差异。它们各自造成多少掉分尚未隔离，不能把全部损失归因于分辨率。

## 同DeepGlobe100给出的约束

|整图一次查询编码，九个共享特征读出|27.546345|9.423|

都是同一冻结100配对、逐例I/U合并的本地探索结果；时延为MPS FP32 B1、模型已加载、单CPU/2线程，包含真实必要输入编码和完整后处理。全部计时样本与各自封存预测逐字节一致。100缓存实验耗时不混入上表，计时5例不能代表100例平均吞吐。

共享版仍能通过区域筛选从24.302504升到27.546345，但对九窗最终输出掉9.797683点。这个具体替换失败，不能直接替代原方法；它也没有证明所有共享骨干设计都失败。快3窗更快且仍高于FoRIS29.377542，但较九窗掉4.605226点，目前同样不能承担“保住37”的承诺。

## 三窗、一窗和布局

三是预算选择，不是理论最优数量。上中下512窗是原九窗编号1/4/7，横向均在256..768，实际覆盖中央50%；其余位置保持全图FoRIS。没有运行过对角三窗，也没有扫描布局。更少视野可能减少高分辨率目标证据，也可能减少干扰，分数不保证单调。全图FoRIS的一次查询视野与“中央一个512局部窗”的输入/尺度不同，不能冒充同条件1窗消融。

## 对后续创新与效率的判断

可以沿卷积/共享骨干的思想继续拆出公共运算，但应保持参考mask定义的任务关系和区域接受/拒绝机制。研究问题应是：共享全局语义的同时，怎样以少量真实局部编码保留关键细节，或在原特征与RGB上形成更好的局部提议；不是把9次编码称为一次batch调用，也不是重复插值增加“视野”数量。

实际候选可优先考虑用合法任务证据决定需要额外局部观察的位置，而不是任意固定三窗；尚无实验成绩，不自动启动新样本、窗口网格或阈值搜索。一次更高分辨率编码也不是天然便宜：token数和自注意力成本必须实测，不能因前向调用只有一次就宣称提速。新增训练模型和权重不属于当前冻结Strong协议。
