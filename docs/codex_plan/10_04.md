# 10_04 计划：SAM3 的候选区域，按每张图相对地挑

交给 Codex 执行。只做这一件事，做完把脚本打印的表原样贴回来。
本文件会在文末持续追加，每次开工前读到文末；追加的内容与前文冲突时，以追加为准。

## 要回答的问题

SAM3 用一张参考图时，公开协议是"打分超过 0.5 的候选区域才留下"，每张图都用同一个 0.5。
把这条固定的线换成跟着每张图走的线（留下打分不低于"本图最高分 × a"的候选），能涨多少？
不用标注，不训练，不加任何输入。

## 为什么做这个（2026-10-04 在已存记录上量的，CPU）

数据：DEV241，SAM3 视觉提示那一路每张图存下的前 20 个候选的打分。读数是查询区域内候选并集的类 mIoU，
配对差相对"打分 > 0.5"，方括号是 95% 区间。脚本：`scripts/sam3_relative_decision.py --approximate`。

| 怎么挑候选 | mIoU | 相对 0.5 |
|---|---:|---|
| 打分 > 0.5（公开协议） | 62.63 | |
| 打分 > 0.3（对照：线低一点，仍然每张图一样） | 65.66 | +3.03 [+0.64, +8.43] |
| 打分 > 0.5，一个都没有时留最高分的那个 | 68.50 | +5.87 [+3.19, +9.05] |
| 打分 ≥ 本图最高分 × 0.7 | 69.65 | +7.03 [+4.78, +11.43] |
| 用标注挑（只作诊断） | 80.09 | +17.46 |
| 给类别名（特权，只作参照） | 72.56 | |

- 241 例里有 55 例没有任何查询候选超过 0.5；其中 36 例最高分的那个候选就在目标上。
- SAM3 打分区分"在目标上／不在目标上"的候选，AUC 是 0.716。
- **这些数还不能当结果。** 后三行的并集是近似的（当作候选互不重叠来算，偏保守），0.7 这个系数是在同一批数据上看出来的，
  分辨率是画布上的，不是主表的原图分辨率。本计划就是把它精确地读一遍。

## 步骤

所有命令在服务器 `/root/autodl-tmp/demo9_transductive_ics` 下执行。当前服务器地址见 `docs/harness/STATUS.md`。

**1. 无卡模式：同步四个脚本并做准备检查（CPU）**

从仓库 `demo_lists/demo9_transductive_ics/scripts/` 复制到服务器 `scripts/`：
`sam3_chain.sh`、`sam3_stitch.py`、`sam3_relative_decision.py`、`experiment_resource_guard.py`。然后：

- 运行链自己先跑 10 例冒烟，再跑 DEV241，再跑 CONFIRM600；`KEEP=1` 让它保留候选区域的位图。
- 两条读数命令是 CPU 的：第一条在 DEV241 上读全部规则；第二条把 DEV 上最好的那条无标注规则冻结，在 CONFIRM600 上读一次。
- 最后一行无论成败都关机。结果在数据盘上，关机不丢。
- 时间依据：上次同一脚本两路提示合计每例 0.71 秒（在另一台实例上量的），841 例约 10 分钟，加模型加载和冒烟。

**3. 贴回结果**

把 `results/sam3_relative_v1.log` 里脚本打印的表原样贴回：DEV 和 CONFIRM 各自的 `canvas reading`、`original reading`，
以及 `FROZEN on DEV:` 那一行。再把 `results/sam3_relative_v1/dev.json`、`confirm.json` 拷回仓库同名路径。

## 怎么读结果

看 CONFIRM600 的 `original reading` 里被冻结的那条规则：

| 结果 | 含义 | 下一份计划 |
|---|---|---|
| 相对 0.5 的区间下端大于 0，而且点估计高于"打分 > 0.3"这个对照 | "判决线要跟着每张图走"在第二个宿主上也成立，而且不需要标注 | 在官方 4×1000 的 episode 上读一次，和 FSS-SAM3 论文的 66.1 放在同一协议下比；再看其他数据集 |
| 赢了 0.5，但没赢过 0.3 | 只是 0.5 定高了，不是"跟着图走"带来的 | 看相对规则错留了哪些候选 |
| 没有增益 | 近似读数误导了 | 在失败账本记一行 |

CONFIRM600 这批图以前被读过多次，不算全新的确认集；全新的确认留给上表第一行的下一份计划。
相对规则默认"查询图里一定有目标"，这和基准的设定、和 FoRIS／INSID3 的做法一致，写论文时要说明。

  我们按作者协议复现 FSS-SAM3 是 59.93（200 例），按拼接协议是 61.09（CONFIRM600）、62.56（DEV241）。

## 追加 3（10-04 晚）：同一次开机里测一个新方法——反向验证

存候选只是辅助。这一段让同一次开机里的 GPU 也用在一个新方法上。**命令仍然不变**，新内容都在 `sam3_relative_fresh.sh` 里。

**为什么是这个方法（依据都是已存数据上量出来的）：**

- 相对规则之后，剩下最大的一块错误是"留下了不在目标上的候选"。DEV241 近似读数里，241 例有 57 例：
  45 例对的和错的都留了，平均 IoU 49；12 例只留了错的，平均 IoU 15。
- SAM3 的正向打分区分"在目标上／不在目标上"的候选，AUC 只有 0.716。再读同一个分数没有用，需要一种新的依据。
- "是同一类"是对称的：如果查询里的某个候选和参考物体是同一类，那么反过来拿这个候选当例子，SAM3 应该能把参考物体找出来。
  参考掩码是已知的，所以这个检查有标准答案，而且不需要查询标注。
- 已知的风险：图池时期在整张掩码上做过类似的往返检查，它能反映漏检（相关 0.72），反映不了多检（0.33）。
  这次是在单个候选区域上做，构造不同；能不能分开对错，正是这次要量的。

**跑什么：** `scripts/sam3_backward_check.py`（新脚本，已写好）。每一例取打分最高的 5 个查询候选，逐个单独当作例子框，
调用和正向完全相同的 SAM3 接口（只是框换了位置），在参考图那一块里读它找回参考掩码的程度。GPU 阶段不读任何查询标注。
然后在 CPU 上打印一张 AUC 表：每个反向信号、以及正向打分，各自把"在目标上"和"不在目标上"的候选分开的程度。

**这一步量的是信号，不是方法分数。** 挑选规则等我看到 AUC 表之后在 DEV241 上定，在 CPU 上精确读（候选位图都在盘上），不用再开机。

**同步的文件变成六个：** 前面五个，加上 `sam3_backward_check.py`。

**整次开机的顺序**（按价值排，中途断了损失最小）：

| 序 | 内容 | GPU 时间（估计） |
|---|---|---|
| 0 | `sam3_chain.sh`：DEV241、CONFIRM600 出候选；CPU 精确读全部规则 | 约 15 分钟 |
| 1 | rest 第 0 片出候选；读数成立时打分并做全新确认 | 约 13 分钟 |
| 2 | 反向验证：先 10 例冒烟，再 DEV241、CONFIRM600；CPU 打印 AUC 表 | 约 23 分钟 |
| 3 | rest 第 1、2 片出候选（不打分） | 约 25 分钟 |
| 4 | rest 第 0 片的反向验证，只在第 2 步显示它带来新信息时跑 | 约 29 分钟 |
| | 关机 | |

合计约 110 到 120 分钟（含每个阶段约 1 分钟的模型加载）。反向验证按"每次调用约 0.35 秒"估的，这是上次两路合计 0.71 秒的一半，
没有单独量过；冒烟阶段会打印实际的每次调用秒数。任何一个 GPU 阶段失败都不会中断后面的阶段。

**贴回的内容再多三样：** 日志里 `backward signal on dev:` 和 `on confirm:` 后面的两张 AUC 表；
`DEV241, proposals kept by relative_0.7: forward score AUC ..., best backward signal AUC ...` 这一行；
三个 `backward ...:` 行（里面有每次调用的秒数）。再把 `results/sam3_relative_v1/backward_*.auc.json` 拷回仓库。

**怎么读：** 看 DEV241 上"被相对规则留下的候选"那张表。

| 结果 | 含义 | 下一步（都在 CPU 上，由我来做） |
|---|---|---|
| 反向信号的 AUC 比正向打分高 0.05 以上 | 反向验证带来了新信息 | 定出"相对规则加反向验证"的挑选规则：DEV241 上选，CONFIRM600 上读，rest 第 0 片复核 |
| 没有高出 | 这种构造下反向验证分不开对错 | 失败账本记一行；下一个候选依据是 FoRIS 证据，可以完全离线做 |

**本地检查过的：** 反向验证脚本用替身模型在 CPU 上走通了同一个循环，自检 5/5；整段流程脚本做过两种空跑
（只生成守卫计划；所有 GPU 阶段都失败时仍能走到结尾）。
**没检查过的：** 真实 SAM3 在"例子框落在查询区域里"时的行为（接口调用和正向完全相同，但这种位置的框没跑过）；实际耗时。
